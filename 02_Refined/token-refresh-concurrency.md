# 토큰 갱신의 동시성

## 핵심 명제

> **회전은 조회가 아니라 상태 변경이다. 상태 변경을 모든 요청이 지나는 자리에 두면, 동시 요청 수만큼 상태가 갈라진다.**

브라우저는 한 페이지를 그리기 위해 요청을 **한 개가 아니라 수십 개** 보낸다. `page.html`, `app.js`, `style.css`, `logo.png`, `/api/me` … 전부 같은 자격 증명을 달고 거의 동시에 출발한다. 인증 필터는 이 전부를 통과시키는 자리다.

## 증상 1 — 동시 요청이 회전을 N번 일으킨다

락도 조건부 갱신도 없이, 필터에서 "액세스 토큰이 만료됐으면 회전한다"를 구현한 경우.

```
t0  스레드1~5  SELECT ... WHERE token_hash = H(R1)  →  5개 전부 "유효" 판정 통과
t1  스레드1    DELETE R1 → INSERT R2 → 응답에 R2
t2  스레드2    DELETE R1 (0 rows, 확인하지 않음) → INSERT R3
t3  스레드3    ... → INSERT R4
t4  스레드4    ... → INSERT R5
t5  스레드5    ... → INSERT R6
```

경합은 **읽기와 쓰기 사이의 틈**에서 발생한다. 스레드 1이 상태를 바꾸기 전에 나머지가 이미 "유효"를 읽어버렸다.

결과:

- `R1`은 사라지고 DB에 **유효한 리프레시 토큰이 5개** 남는다.
- 클라이언트가 실제로 쥔 것은 그중 **하나뿐**이다.
- 나머지 4개는 **고아 토큰** — 서버는 유효하다고 보는데 아무도 손에 쥐고 있지 않은 토큰.
- 5개 스레드 전부 `R1`을 "유효" 상태에서 읽었으므로 **재사용 탐지가 발동조차 하지 않는다.**

> 고아 토큰은 단순한 쓰레기가 아니다. **주인 없이 유효한 인증 수단**이므로 공격 표면이 그만큼 넓어진다.

## 증상 2 — 정적 리소스 요청에서 발급된 토큰은 증발한다

**응답 커밋 문제.** 필터에서 `response.getWriter().write(json)`을 호출하면 응답이 커밋된다.

| 이후 동작 | 결과 |
|---|---|
| `filterChain.doFilter()` 호출 | 뒤의 핸들러가 다시 쓰려다 `IllegalStateException`, 혹은 JSON 뒤에 CSS가 이어 붙은 깨진 바디 |
| `doFilter()` 생략 | CSS가 영영 나가지 않음 → 스타일 없는 페이지 |

어느 쪽도 정상 동작이 아니다.

**더 결정적인 문제.** `<img src>`, `<link rel="stylesheet">`, `<script src>`는 **브라우저가 직접** 보내는 요청이다.

- axios 인터셉터도 `fetch().then()`도 붙지 않는다.
- **응답 바디를 읽을 JS가 존재하지 않는다.**
- 따라서 그 응답에 실린 새 리프레시 토큰은 **아무도 받지 못하고 증발**한다. 서버 DB에만 남는다.

클라이언트는 여전히 폐기된 옛 토큰을 들고 있고, 다음 요청에서 로그아웃된다.

## 처방 1 — 회전을 한 곳으로 모은다 (위치 설계)

| | 필터에서 회전 (모든 엔드포인트) | `/auth/refresh` 한 곳에서만 회전 |
|---|---|---|
| 요청 5개 동시 유입 | 회전 **5번** | 회전 **1번** |
| 고아 토큰 | 4개 | **0개** |
| 정적 리소스 응답 | JSON 오염 / 응답 커밋 충돌 | 정상 |
| 새 토큰 전달 | `<img>`·`<link>` 응답은 JS가 못 읽어 증발 | `Set-Cookie` → 브라우저가 자동 저장 |

> **인증 필터의 책임 = 액세스 토큰 검증 + `SecurityContext` 세팅 + 실패 시 401. 그 이상은 하지 않는다.**
> 상태를 바꾸는 일은 클라이언트의 명시적 트리거를 받아 전용 엔드포인트가 수행한다.

```
1. 브라우저가 logo.png, app.js, style.css, /api/me 동시 요청 (만료된 액세스 토큰 첨부)
2. 필터는 회전하지 않는다. 전부 401.
3. 클라이언트 인터셉터가 401 을 보고 → /auth/refresh 호출
4. 서버가 여기서만 회전 → 새 액세스 토큰 + 새 리프레시 토큰(HttpOnly 쿠키)
5. 인터셉터가 실패했던 요청들을 재시도 → 전부 성공
```

고아 토큰이 0개인 이유: 새 토큰은 `Set-Cookie`로 브라우저가 자동 저장하므로 **주인이 확실하고**, 이전 토큰은 폐기 상태라 유효하지 않다. "유효한데 주인 없는 토큰"이 생길 자리가 없다.

## 처방 2 — 클라이언트 single-flight

401 이 4개 돌아오면 인터셉터는 `/auth/refresh`를 **4번** 부른다. 경로만 모았을 뿐 경합은 그대로다.

```js
let refreshing = null;               // 진행 중인 갱신 Promise 하나

function refresh() {
  if (!refreshing) {
    refreshing = api.post('/auth/refresh')
      .finally(() => { refreshing = null; });   // 끝나면 비운다
  }
  return refreshing;                 // 뒤따르는 호출은 같은 Promise 를 받는다
}

// 401 인터셉터
await refresh();                     // 새로 만들지 않고 기다린다
return api.request(original.config); // 그 다음 원래 요청 재시도
```

> **핵심은 "호출을 안 한다"가 아니라 "이미 날아간 갱신을 기다렸다가 이어서 재시도한다"이다.**
> 그냥 건너뛰면 그 요청(예: `style.css`)은 영영 실패한 채로 남는다.

## 처방 3 — 서버 grace period + 원자적 갱신

클라이언트만 믿을 수 없다. 탭 두 개, 웹과 모바일 앱 동시 실행은 인터셉터로 막히지 않는다.

이미 폐기된 토큰이 들어왔을 때, **시간 축**으로 두 경우를 가른다.

| 유입 시점 | 해석 | 서버 동작 |
|---|---|---|
| 회전 후 수 초 이내 (grace period) | 정상 동시 요청 | **회전하지 않고** 직전 발급분을 그대로 재응답 (**멱등**) |
| grace period 밖 (예: 3일 뒤) | 탈취 — 정상 클라이언트라면 이미 갈아탔을 시간 | **family 전체 폐기** [[refresh-token-rotation]] |

멱등 재응답을 하려면 이전 토큰 행이 "이 토큰이 회전되면서 나온 결과물"을 유예 시간 동안 들고 있어야 한다(`replaced_by` 등).

> 유예 구간 안에서 **다시 회전시키면 안 된다.** 그러면 요청 수만큼 회전이 다시 일어나 유예 구간을 둔 의미가 사라진다.

그리고 경합 자체는 "조회 후 갱신"이 아니라 **조건부 원자 갱신**으로 닫는다.

```sql
UPDATE refresh_token
   SET used = true, rotated_at = now()
 WHERE token_hash = ? AND used = false;
-- 영향 행 수 1 → 이 요청이 회전 승자
-- 영향 행 수 0 → 이미 누가 회전시켰다. 시간 축으로 판정 후 멱등 재응답 or family 폐기
```

읽고 나서 판단하는 대신, **판단을 UPDATE 조건에 넣어** 승자를 DB가 하나만 뽑게 한다.

> [!WARNING]
> **오답 코너**
>
> - **"회전은 모든 엔드포인트에서 일어나야 한다"** — 그것이 고아 토큰·토큰 증발·랜덤 로그아웃의 **원인**이다. 회전은 상태 변경이므로 트리거는 하나여야 한다.
> - **"동시 요청 5개가 와도 결국 마지막 하나만 남는다"** — 남는 건 하나가 아니라 **유효한 토큰 5개**다. `R1`은 사라지고 주인 없는 토큰이 4개 쌓인다.
> - **"응답에 새 토큰을 실어 보내면 클라이언트가 받는다"** — `<img>`·`<link>`·`<script src>` 응답 바디를 읽을 JS는 존재하지 않는다. 브라우저가 직접 보낸 요청에는 인터셉터가 붙지 않는다.
> - **"필터에서 JSON 쓰고 `doFilter()` 부르면 둘 다 나간다"** — 응답이 이미 커밋되어 `IllegalStateException` 또는 깨진 바디가 나간다.
> - **"single-flight 는 뒤따르는 401 의 갱신 호출을 막는 것"** — 막는 게 아니라 **공유해서 기다리는 것**이다. 기다린 뒤 원래 요청을 재시도해야 그 리소스가 살아난다.
> - **"유예 구간 안의 요청에는 새로 발급해 준다"** — 발급하면 회전이 또 일어난다. **직전 발급분을 그대로 재응답(멱등)** 해야 한다.
> - **"클라이언트에서 single-flight 하면 서버는 안 고쳐도 된다"** — 탭 두 개·다중 디바이스는 클라이언트가 막을 수 없다. 서버가 독립적으로 방어해야 한다.

## 복습 체크

- [ ] 락 없는 회전에서 요청 5개가 동시에 오면 DB와 클라이언트에 각각 무엇이 남는가?
- [ ] 고아 토큰의 정의와, 그것이 왜 단순한 쓰레기가 아닌지 말할 수 있는가?
- [ ] 정적 리소스 요청에서 회전하면 새 토큰이 왜 증발하는가? (두 가지 이유)
- [ ] 인증 필터의 책임 경계를 한 문장으로 말할 수 있는가?
- [ ] single-flight 에서 뒤따르는 요청이 해야 하는 두 단계는?
- [ ] `used` 토큰이 200ms 뒤 / 3일 뒤에 들어온 경우를 서버는 각각 어떻게 처리해야 하는가?
- [ ] 조건부 원자 갱신이 "조회 후 갱신"보다 나은 이유를 영향 행 수 관점에서 설명할 수 있는가?
