# 인터프리터와 JIT 컴파일러

## 개념 정의

JVM 실행 엔진이 바이트코드를 실행하는 **두 가지 방식**.

| | 인터프리터 | JIT 컴파일러 |
|---|---|---|
| 방식 | 바이트코드를 **한 줄씩** 읽어 즉시 실행 | 코드 구간을 **통째로 기계어로 컴파일**해 캐싱 |
| 시작 | 빠름 | 느림 (컴파일 비용 선지불) |
| 반복 실행 | 느림 (매번 다시 해석) | 빠름 (캐싱된 기계어 재사용) |

## 작동 원리

### 왜 둘 다 필요한가

- **인터프리터만 쓰면** → 루프처럼 반복되는 코드가 계속 느리다.
- **전부 JIT 컴파일하면** → 프로그램 **시작이 느려지고**, 딱 한 번 실행되고 버려질 코드에 들인
  컴파일 비용이 그대로 낭비된다.

**두 방식의 장단점이 정확히 반대**이므로 JVM 은 섞어 쓴다.

### 핫스팟 판정

JVM 은 메서드와 루프마다 **실행 횟수 카운터**를 둔다.
카운터가 **임계값(threshold)을 넘은 구간 = 핫스팟(HotSpot)** 으로 판정하고, 그것만 골라 JIT 컴파일한다.

```
실행 시작
  → 전부 인터프리터로 (빠른 시작)
  → 카운터 누적
  → 임계값 초과 구간만 JIT 컴파일 → 이후 그 구간은 기계어로 실행
```

Oracle 기본 JVM 의 이름이 **"HotSpot JVM"** 인 이유가 이 전략이다.

JIT 은 단순 번역을 넘어 **런타임 정보를 활용한 최적화**를 한다 — 메서드 인라이닝, 죽은 코드 제거,
실제 타입이 하나뿐인 호출의 단일화(동적 바인딩 비용 제거 — [[overriding-vs-overloading-binding]]) 등. 정적 컴파일러가 알 수 없는 "실제로 어떻게 실행되는가"를
알기 때문에 가능한 최적화이며, 가정이 깨지면 **역최적화(deoptimization)** 로 인터프리터로 되돌아간다.

## 트레이드오프 / 한계

- **워밍업(warm-up) 구간이 존재한다.** 기동 직후는 아직 인터프리터라 느리다.
  → 성능 벤치마크에서 초반 측정치를 버리는 이유. 배포 직후 순간적으로 응답이 느려지는 것도 이 때문.
- **짧게 살고 죽는 프로세스에는 불리하다** — CLI 도구, 서버리스 함수처럼 수명이 짧으면
  JIT 이 이득을 볼 기회 자체가 없다. → AOT 컴파일(GraalVM 네이티브 이미지)이 이 지점을 공략한다.
- **컴파일된 코드와 메타데이터가 메모리를 차지**한다(코드 캐시).
- JIT 최적화 결과가 실행마다 달라질 수 있어 **성능이 완전히 결정론적이지 않다.**

> [!WARNING]
> **오답 코너**
> - **"JIT 이 더 좋으니 전부 JIT 하면 된다"** — 시작이 느려지고 1회성 코드에 컴파일 비용이 낭비된다.
> - **"JVM 이 '자주 쓰일 코드'를 미리 예측한다"** — 예측이 아니라 **실행 횟수 카운터가 임계값을 넘었는지**
>   보는 사후 판정이다.
> - **"인터프리터는 이제 안 쓴다"** — 시작 구간과 역최적화 이후에 여전히 쓰인다.
> - **"JIT 은 바이트코드를 기계어로 번역만 한다"** — 런타임 정보 기반 최적화(인라이닝 등)까지 수행한다.
