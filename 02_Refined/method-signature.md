# 메서드 시그니처

## 개념 정의

> **시그니처 = 메서드 이름 + 매개변수 타입 목록(개수·순서)**

```java
int sum(int a, int b) { ... }      // 이미 있음

long sum(int a, int b)   { ... }   // (가) ❌ 반환 타입만 다름 → 같은 시그니처
int  sum(int x, int y)   { ... }   // (나) ❌ 매개변수 이름만 다름 → 같은 시그니처
int  sum(long a, int b)  { ... }   // (다) ⭕ 타입이 다름
int  sum(int a, long b)  { ... }   // (라) ⭕ 순서가 다름
```

| 바꾼 것 | 시그니처에 포함? |
|---|---|
| 매개변수 타입·개수·순서 | ⭕ → 오버로딩 가능 |
| 반환 타입 | ❌ |
| 매개변수 이름 | ❌ (컴파일러에겐 `sum(int, int)` 일 뿐) |
| 접근 제어자, `throws` | ❌ |

## 작동 원리 — 왜 반환 타입은 빠지나

```java
sum(1, 2);   // 결과를 변수에 담지 않고 그냥 호출 — 합법
```

- 컴파일러는 각 메서드의 반환 타입을 **알고 있다**(선언에 적혀 있다).
- 모르는 건 **호출하는 쪽이 어느 것을 원하는지**다. 호출하는 줄에서 보이는 건 **이름과 인자뿐**이고 결과를 버리는 호출도 합법이라, 반환 타입으로는 고를 단서가 없다.
- 그래서 고르는 기준이 될 수 있는 **이름 + 매개변수 타입**만 시그니처가 된다.

오버로딩은 이 시그니처로 **컴파일할 때** 호출 대상을 정한다(정적 바인딩). 오버라이딩은 같은 시그니처를 자식이 다시 구현하는 것이고, 실행 중 실제 객체로 정해진다(동적 바인딩) ([[overriding-vs-overloading-binding]]).

## 트레이드오프 / 한계

- 오버로딩 후보가 여럿이면 컴파일러는 정해진 순서(정확히 일치 → 확대 변환 → 박싱 → 가변 인자)로 고른다. 가변 인자가 마지막이라, 고정 개수 오버로드가 있으면 그쪽이 먼저 선택된다 ([[varargs]]).
- 이름만 같고 매개변수 타입이 다른 메서드는 **별개의 메서드**다. 부모의 `print(Object)` 를 자식에서 `print(String)` 으로 "덮어썼다"고 착각하면 오버라이딩이 아니라 오버로딩이 된다 ([[overriding-vs-overloading-binding]]).

> [!WARNING]
> **오답 코너**
> - **"반환 타입이 다르면 오버로딩할 수 있다"** — 반환 타입은 시그니처에 들어가지 않는다. 같은 시그니처라 컴파일 에러.
> - **"컴파일러가 반환 타입을 몰라서 막는다"** — 컴파일러는 반환 타입을 **안다**. 모르는 건 **호출부가 어느 것을 원하는지**다.

## 면접 답변

> "메서드 시그니처는 메서드 이름과 매개변수의 타입·개수·순서로 구성되고, 반환 타입이나 매개변수 이름은 포함되지 않습니다. 호출하는 코드에서는 이름과 넘기는 인자만 보이고 반환값은 버릴 수도 있어서, 컴파일러가 반환 타입으로는 어느 메서드를 부를지 고를 수 없기 때문입니다."
