# 비밀번호는 BCrypt, 리프레시 토큰은 SHA-256인 이유

## 배운 개념

### 핵심 결론

**알고리즘이 저장 대상을 정하는 게 아니라, 저장 대상의 성질이 알고리즘을 정한다.**

판단 축은 두 개다.

1. 원본 값의 **엔트로피** (= 공격자가 뒤져야 할 후보의 개수)
2. **오프라인 공격**이 가능한가 (= 서버가 시도 횟수에 개입할 수 있는가)

### 판단 기준표

| 값 | 생성 주체 | 탐색 공간 | 공격 형태 | 저장 방식 |
|---|---|---|---|---|
| 비밀번호 | 사람 | ~10¹² | 오프라인 | **BCrypt** |
| 리프레시 토큰 | `SecureRandom` 256bit | ~10⁷⁷ | 사실상 불가 | **SHA-256** |
| 이메일 인증 토큰 | `SecureRandom` | ~10⁷⁷ | 사실상 불가 | **SHA-256** |
| 비밀번호 재설정 토큰 | `SecureRandom` | ~10⁷⁷ | 사실상 불가 | **SHA-256** |
| 초대 코드 8자리 | 서버(단축 문자셋 32자) | 2⁴⁰ ≈ 10¹² | 온라인 | **SHA-256 + 레이트 리밋** |

> 초대 코드의 8자리·32자 문자셋은 이번 세션에서 가정한 값. 실제 프로젝트 값 확인 필요.

---

### 축 1. 엔트로피가 알고리즘을 결정한다

공격자가 해시를 깨는 절차는 네 단계의 반복이다.

1. 원본 후보값을 하나 만든다
2. 그 후보를 해시한다
3. DB의 해시값과 비교한다
4. 안 맞으면 1번으로

**알고리즘 속도는 2번의 1회 비용만 결정한다.** 총 소요 시간의 나머지 한 축은 1번이 만들어야 할 **후보의 개수**, 즉 엔트로피다.

- 비밀번호: 사람이 만들어 `password123`·이름+생년월일 같은 패턴에 몰린다. 유출 사전 + 규칙 변형까지 쳐서 현실적 탐색 공간 **약 10¹²**
- 리프레시 토큰: `SecureRandom` 256비트 → **2²⁵⁶ ≈ 10⁷⁷**

여기에 BCrypt(cost 12, 1회 ≈ 250ms)를 씌우면 어떻게 되는가.

- 비밀번호: 10¹² × 0.25초 ≈ **8,000년** → SHA-256이면 GPU로 몇 분이면 끝날 걸 8,000년으로 바꿨다. **방어가 성립한다.**
- 리프레시 토큰: 10⁷⁷ → 10⁸² → **어차피 둘 다 우주가 끝날 때까지 못 뚫는다. 의미 없음.**

> **원칙**: BCrypt는 부족한 엔트로피를 연산 비용으로 메우는 도구다. 탐색 공간이 **현실적으로 완주 가능한 크기일 때만** 1회 비용을 늘리는 게 방어가 된다. 이미 완주 불가능하면 배수를 곱해봐야 아무것도 바뀌지 않는다.

---

### 축 2. 조회 가능성이 알고리즘을 제약한다

해시는 되돌릴 수 없으므로, 서버는 **"DB에서 그 행을 어떻게 찾느냐"**를 먼저 해결해야 한다.

**로그인 — 찾기와 검증이 분리된다**

```
클라이언트가 보낸 것: id = "alice", password = "hunter2"
```

```sql
SELECT * FROM users WHERE id = 'alice'
```

**비밀번호가 아니라 아이디로 찾는다.** 행을 특정한 뒤 `BCrypt.matches("hunter2", 저장된해시)`. BCrypt는 저장된 해시 문자열 안에 salt가 박혀 있어서 그걸 꺼내 재계산·비교할 수 있다. → **BCrypt 연산 1회로 끝난다.**

**토큰 갱신 — 별도의 조회 키가 없다**

```
클라이언트가 보낸 것: token = "a3f9c2...8e1b"  (이게 전부)
```

```sql
SELECT * FROM refresh_tokens WHERE token_hash = ?
```

이 쿼리가 성립하려면 **같은 입력에 항상 같은 출력**이 나와야 한다 — 해시가 **결정적(deterministic)**이어야 한다.

| | salt | 결정적? | 조회 |
|---|---|---|---|
| BCrypt | 매번 랜덤 | ✗ | `WHERE token_hash = ?` 자체가 성립 안 함 → **인덱스를 못 탄다** |
| SHA-256 | 없음 | ✓ | `token_hash` 유니크 인덱스 → **O(log n)** |

BCrypt로 저장했다면 전체 스캔 + **행마다 BCrypt 연산**이 된다. 10만 행이면 최악의 경우 10만 × 0.25초 ≈ **7시간**. 토큰 갱신 요청 한 건에.

---

### 축 3. 호출 빈도가 비용의 무게를 바꾼다

액세스 토큰 15분 만료, 하루 8시간 사용, 사용자 1만 명 기준.

| | 하루 호출 수 | × 250ms |
|---|---|---|
| 비밀번호 검증(로그인) | 1만 회 | 2,500초 — 무시할 만함 |
| 리프레시 토큰 검증 | 8h ÷ 15m = 32회 × 1만 = **32만 회** | 8만 초 ≈ **CPU 22시간** |

**관점 전환**: BCrypt의 느림은 공격자만 느리게 만드는 게 아니다. **서버도 똑같이 느려진다.** 그 거래가 성립하는 건 "내가 1회 낼 때 공격자는 10¹²회 낸다"는 **비대칭** 덕분인데, 리프레시 토큰에서는 공격자가 애초에 그 판에 들어오지 않으므로(10⁷⁷) **비용만 내가 혼자 부담**한다.

게다가 BCrypt는 설계상 병렬화·메모리 최적화를 일부러 방해하므로 코어를 늘려도 깔끔히 나눠지지 않는다.

성능 문제로 끝나지 않는다. 공격자가 아무 문자열이나 리프레시 토큰이라며 초당 수천 건 던지면 서버는 매번 250ms를 태운다. → **방어 수단이 그대로 DoS 증폭기가 된다.**

---

### 축 4. 그럼에도 해시는 씌운다 (왜 평문이 아닌가)

- **평문 저장**: DB 유출 = 그 값을 헤더에 넣기만 하면 **즉시 전 사용자 계정 탈취**. 공격자 연산 0회.
- **해시 저장**: 공격자가 얻은 건 검증에 쓸 수 없는 값. 원본을 얻으려면 10⁷⁷을 뚫어야 하고 그건 불가능.

> 해시의 목적은 **"푸는 데 시간이 걸리게 하는 것"이 아니라 "값을 검증에 쓸 수 없게 만드는 것"**이다.

요구되는 성질이 **비가역성 하나뿐**이므로 가장 싼 도구(SHA-256)를 쓴다. BCrypt가 추가로 파는 상품(연산 지연)은 이 시나리오에서 살 이유가 없는 물건이다.

---

### 축 5. 오프라인 공격 vs 온라인 공격 — 초대 코드 사례

초대 코드는 **양쪽 요구가 충돌**하는 케이스다.

- 저엔트로피(2⁴⁰) → 무차별 대입 방어가 필요 → BCrypt?
- 코드만 받아서 그룹을 찾아야 함 → 결정적 해시가 필요 → SHA-256?

BCrypt는 앞을 만족하지만 뒤를 못 하고, SHA-256은 뒤를 만족하지만 앞을 못 한다.

**해법은 알고리즘 선택 바깥에 있다.**

| | 판정 주체 | 공격자 위치 | 서버 개입 | 방어 수단 |
|---|---|---|---|---|
| DB 유출된 해시 | 공격자 자신 | 자기 장비 | **불가능** | 해시 비용(BCrypt)뿐 |
| 초대 코드 | **서버** | 네트워크 너머 | **가능** | **레이트 리밋** |

GPU가 초당 100억 회를 돌릴 수 있는 건 공격자가 **자기 장비에서** 계산할 때 얘기다. 초대 코드는 정답 여부를 **서버가 판정**하므로 공격자는 매 시도마다 네트워크를 타야 한다.

- 레이트 리밋 없음: 2⁴⁰ ÷ 100억/초 = **100초**면 전수 조사 끝
- IP·계정당 분당 5회: 같은 2⁴⁰이 **수십만 년**

탐색 공간의 크기는 그대로인데 **1회 시도 비용을 서버가 강제로 올린** 것이다.

오프라인 공격이 봉쇄되면 남는 위협은 DB 유출뿐이고, 그때 필요한 건 비가역성 하나. → **SHA-256 + 레이트 리밋 + 짧은 유효기간 + 재발급 수단**의 조합이 실무적 답.

---

### 최종 원칙

> **BCrypt가 필요한 건 "저엔트로피"가 아니라 "저엔트로피 + 오프라인 공격 가능"이 겹칠 때다.**
> 비밀번호가 유일하게 그렇다. 사람이 만들었고, 해시가 털리면 서버가 아무것도 막을 수 없다.

## 오답 · 헷갈린 점 (정정 포함)

### ① 난이도 차이의 원인을 "알고리즘 성질"로 봤다
- **틀린 생각**: 비밀번호가 더 안전한 건 BCrypt가 더 강한 알고리즘이라서.
- **모순**: 그렇다면 리프레시 토큰의 SHA-256은 "보안을 덜 챙긴 나쁜 설계"가 된다. 그런데 그건 실무 **표준 권장 방식**이다.
- **정정**: 원인은 **원본 값의 엔트로피**. 엔트로피가 무엇을 요구하는지가 먼저 정해지고, **알고리즘은 그 결과로 고르는 것**이다. 원인과 결과가 뒤집혀 있었다.

### ② 256비트 = 후보 256개로 이해했다 ★가장 큰 오개념
- **틀린 생각**: "2번은 256번 안에 해결할 수 있다."
- **정정**: **비트는 개수가 아니라 자릿수**다.
  - 4자리 숫자 PIN → 자릿수마다 10가지 → 10⁴ = 10,000개
  - **8비트** → 자릿수마다 2가지 → 2⁸ = **256개** ← 256개가 나오는 건 8비트다
  - **256비트** → **2²⁵⁶ ≈ 10⁷⁷개** (관측 가능한 우주의 원자 수가 약 10⁸⁰)

### ③ "해시가 풀리는 동안 시간을 벌어 토큰이 재발급되게 한다"
- **틀린 생각**: 해시 저장의 이점은 공격자가 푸는 데 걸리는 시간 동안 토큰이 만료되는 것.
- **왜 틀렸나**: 이건 비밀번호의 사고방식(8,000년 = 시간 벌기)을 그대로 가져온 것.
- **정정**: 고엔트로피 값은 **시간이 걸리는 게 아니라 경로가 아예 닫혀 있다.** "언젠간 풀리지만 그 전에 만료되니 괜찮다"가 아니라 **"영원히 안 풀린다"**. 해시의 역할은 시간 벌기가 아니라 **값의 무용지물화**.

### ④ 이메일 인증 토큰의 엔트로피를 "비밀번호에 가깝다"고 봤다
- **정정**: **엔트로피는 용도가 아니라 생성 주체가 정한다.**
  - 사람이 만들면 → 패턴에 몰린다 → 저엔트로피
  - `SecureRandom`이 만들면 → 패턴 없음 → 고엔트로피
  - 인증 토큰이든 리프레시 토큰이든 세션 ID든, 서버가 난수로 만들었으면 **전부 같은 동네**다.
- **부수적 논리 역전**: 이때 근거로 "비교 비용이 굉장히 많이 든다"를 들었는데, 그건 오히려 **BCrypt를 쓰면 안 되는 이유**였다. BCrypt를 쓸 근거로 인용해서 논리가 뒤집혀 있었다.

### ⑤ 2⁴⁰을 "엄청 큰 숫자"로 봤다
- **정정**: 2⁴⁰ ≈ **1조(10¹²)**. 2²⁵⁶ ≈ 10⁷⁷. **자릿수로 12자리 대 77자리.**
- 초대 코드는 리프레시 토큰 쪽이 아니라 **비밀번호(10¹²)와 같은 동네**다.
- 결과적으로 "BCrypt"라는 답은 맞았지만 근거가 정반대였다. 이유는 "엄청 커서"가 아니라 **"현실적으로 완주 가능한 크기라서"**.

### ⑥ BCrypt의 적용 조건을 "공격당할 확률이 높을 때"로 표현했다
- **왜 모호한가**: 두 테이블 다 똑같이 유출됐으니 공격받을 확률은 동일하다.
- **정정**: 조건은 확률이 아니라 **① 탐색 공간이 완주 가능한 크기 + ② 오프라인 공격 가능**의 교집합.

## Q&A

**Q. 같은 DB 덤프인데 비밀번호 해시와 리프레시 토큰 해시의 공격 난이도가 왜 다른가?**
A. 알고리즘이 아니라 원본 엔트로피 때문. 비밀번호는 후보 10¹²개(사람이 만들어 패턴에 몰림), 리프레시 토큰은 10⁷⁷개(`SecureRandom` 256비트). 전자는 완주 가능하고 후자는 불가능하다.

**Q. 리프레시 토큰에 BCrypt를 쓰면 왜 작동 자체가 곤란해지는가?**
A. 두 가지. ① **조회 불가** — BCrypt는 salt가 랜덤이라 비결정적이고, 토큰 갱신 요청에는 아이디 같은 별도 조회 키가 없어서 `WHERE token_hash = ?`로 찾아야 하는데 인덱스를 못 탄다. ② **행 수만큼 연산** — 전체 스캔 + 행마다 BCrypt. 10만 행이면 요청 한 건에 7시간.

**Q. 로그인은 BCrypt인데 왜 같은 문제가 안 생기나?**
A. 아이디라는 별도 조회 키가 있어 `WHERE id = ?`로 행을 먼저 특정할 수 있다. BCrypt 연산은 특정된 한 행에 대해 딱 1회. **"찾기"와 "검증"이 분리**되어 있다.

**Q. 그럼 왜 리프레시 토큰을 평문으로 저장하면 안 되나?**
A. DB 유출 시 공격자는 그 값을 헤더에 넣기만 하면 즉시 계정 탈취(연산 0회). 해시 한 겹의 목적은 시간 벌기가 아니라 **그 값을 검증에 쓸 수 없게 만드는 것**. 요구되는 성질이 비가역성 하나뿐이라 가장 싼 SHA-256으로 충분하다.

**Q. 저엔트로피인 초대 코드(2⁴⁰)는 그럼 BCrypt인가?**
A. 아니다. 조회 요구와 충돌해서 자리가 없다. 대신 **공격 형태가 다르다** — 정답 판정을 서버가 하므로 **온라인 공격**이고, 레이트 리밋으로 1회 시도 비용을 강제로 올릴 수 있다. 분당 5회면 2⁴⁰ 완주에 수십만 년. → SHA-256 + 레이트 리밋 + 짧은 유효기간 + 재발급.

**Q. 한 줄로 요약하면?**
A. **BCrypt는 저엔트로피와 오프라인 공격이 겹칠 때만 필요하다. 비밀번호가 유일하게 그렇다.**
