## 배운 개념

### 1. 회전(rotation)이 주는 것은 "차단"이 아니라 "탐지"다

회전 자체는 공격자를 막지 못한다. 순서를 보면 명확하다.

```
1. 공격자가 리프레시 토큰 R1을 탈취
2. 공격자가 먼저 R1로 갱신 → 서버가 R2 발급 → R2는 공격자 손에 있음
3. 원래 사용자는 여전히 R1 보유 → 갱신 시도 → 실패
```

즉 회전만 있으면 **밀려나는 쪽은 오히려 정상 사용자**다.

회전의 진짜 값은 3번에서 서버가 얻는 신호다 — **"이미 소비된 토큰이 다시 들어왔다"**.
정상 클라이언트에서는 절대 발생하지 않는 사건이므로 이는 탈취의 증거이고,
서버는 그 순간 해당 토큰이 속한 **체인(family) 전체를 폐기**해야 한다.
그래야 이미 R2로 갈아탄 공격자까지 함께 끊긴다.

→ 따라서 이전 토큰을 **DELETE 하면 안 된다**. 삭제하면 "폐기된 토큰"과 "존재한 적 없는 쓰레기 토큰"을
  구분할 수 없어 탐지 신호가 소멸한다. `used` / `rotated_at` 마킹 + `family_id`로 남겨야 한다.

### 2. 회전을 필터(모든 엔드포인트)에서 하면 벌어지는 일

락도 조건부 업데이트도 없는 상태에서, 페이지 새로고침으로 요청 5개가 동시에 들어온 경우:

```
t0  스레드1~5  SELECT ... WHERE hash = H(R1)  →  5개 전부 "유효" 판정 통과
t1  스레드1    DELETE R1 → INSERT R2 → 응답에 R2
t2  스레드2    DELETE R1 (0 rows, 확인 안 함) → INSERT R3
t3  스레드3    ... → INSERT R4
t4  스레드4    ... → INSERT R5
t5  스레드5    ... → INSERT R6
```

결과:

- `R1`은 사라지고 DB에 **유효한 토큰 5개**(R2~R6)가 남는다.
- 클라이언트가 실제로 쥔 건 그중 **하나뿐**. 나머지 4개는 **고아 토큰**
  (= 서버는 유효하다고 보는데 아무도 손에 쥐고 있지 않은 토큰) → 인증 수단이 늘어 공격 표면이 넓어진다.
- 5개 스레드 전부 R1을 "유효" 상태에서 읽었으므로 **재사용 탐지가 발동조차 하지 않는다.**

### 3. 정적 리소스 요청에서 회전하면 새 토큰이 증발한다

- **응답 커밋 문제**: 필터에서 `response.getWriter().write(json)` 후 `doFilter()`를 호출하면,
  뒤의 핸들러가 다시 응답에 쓰려다 `IllegalStateException`이 나거나 JSON 뒤에 CSS가 이어 붙은 쓰레기 바디가 나간다.
  반대로 `doFilter()`를 생략하면 CSS가 영영 안 나가 스타일 없는 페이지가 된다.
- **더 결정적인 문제**: `<img>`, `<link>`, `<script src>`는 **브라우저가 직접** 보내는 요청이라
  axios 인터셉터도 `fetch().then()`도 붙지 않는다. **응답 바디를 읽을 JS가 존재하지 않는다.**
  → 그 요청에서 발급된 새 리프레시 토큰은 아무도 받지 못하고 증발하고, DB에만 남는다.

### 4. 설계 비교

| | 필터에서 회전 (모든 엔드포인트) | `/auth/refresh` 한 곳에서만 회전 |
|---|---|---|
| 요청 5개 동시 유입 | 회전 5번 | 회전 1번 |
| 고아 토큰 | 4개 | 0개 |
| 정적 리소스 응답 | JSON 오염 / 응답 커밋 충돌 | 정상 |
| 새 토큰 전달 | `<img>`·`<link>` 응답은 JS가 못 읽어 증발 | `Set-Cookie`로 브라우저가 자동 저장 |

**필터의 책임 = 액세스 토큰 검증 + 인증 정보(SecurityContext) 심기 + 실패 시 401.**
상태를 바꾸는 일(회전)은 전용 엔드포인트가 클라이언트의 명시적 트리거로 수행한다.

```
1. 브라우저가 logo.png, app.js, style.css, /api/me 동시 요청 (만료된 액세스 토큰 첨부)
2. 필터는 회전 안 함. 그냥 전부 401.
3. 클라이언트 axios 인터셉터가 401을 보고 → /auth/refresh 호출
4. 서버가 여기서만 회전 → 새 액세스 토큰 + 새 리프레시 토큰(HttpOnly 쿠키)
5. 인터셉터가 실패했던 요청들을 재시도 → 전부 성공
```

### 5. 저장 위치: localStorage → HttpOnly 쿠키

```
Set-Cookie: refreshToken=...; HttpOnly; Secure; SameSite=Strict; Path=/auth/refresh
```

- `HttpOnly` — `document.cookie`로도 못 읽는다. XSS로 스크립트가 주입돼도 **토큰 값 자체는 유출 불가**.
  `localStorage`는 정확히 반대로 XSS 한 방에 통째로 털린다.
- `SameSite` — 쿠키가 자동으로 실려 가는 성질을 악용하는 **CSRF** 차단.
  공격자 사이트의 `<form action="https://my-app.com/auth/refresh" method="post">`가 자동 submit되면,
  브라우저는 "그 도메인으로 가는 요청"이라는 이유만으로 쿠키를 붙여 보낸다.
  `SameSite=Strict`(또는 `Lax`)가 "다른 사이트에서 시작된 요청에는 붙이지 마"라고 지시하는 것.
- `Path` — 애초에 `logo.png` 요청에는 쿠키가 실려 가지도 않는다.

### 6. 동시성은 클라이언트·서버 양쪽에서 막는다

**클라이언트 — single-flight**
첫 401이 갱신 Promise를 만들어 변수에 저장한다. 뒤따르는 401들은 새로 만들지 않고
그 Promise를 `await`한 뒤 원래 요청을 재시도한다. 갱신이 끝나면 변수를 비운다.
(핵심: "호출을 안 한다"가 아니라 "진행 중인 갱신을 기다렸다가 이어서 재시도한다")

**서버 — grace period + 원자적 갱신**
탭 2개, 모바일 앱 동시 실행 등은 인터셉터로 막을 수 없으므로 서버가 독립적으로 방어해야 한다.

| `used` 토큰 유입 시점 | 해석 | 서버 동작 |
|---|---|---|
| 회전 후 수 초 내 (grace period) | 정상 동시 요청 | **회전하지 않고** 직전 발급분을 그대로 재응답 (**멱등**) |
| grace period 밖 (예: 3일 뒤) | 탈취 | **체인(family) 전체 폐기** |

추가로, "조회 후 갱신"이 아니라 `UPDATE ... WHERE used = false` 같은
**조건부 갱신 + 영향 행 수 확인**으로 경합 자체를 원자적으로 차단한다.

## 오답·헷갈린 점

- **"회전하면 공격자가 더 이상 못 쓴다"**
  → 회전은 차단이 아니라 **탐지**다. 먼저 쓴 쪽이 새 토큰을 가지므로 밀려나는 건 오히려 정상 사용자다.
  회전의 값은 "이미 쓰인 토큰의 재유입"이라는 신호를 얻는 데 있다.

- **"이전 토큰은 삭제한다"**
  → 삭제하면 "폐기된 토큰"과 "존재한 적 없는 토큰"을 구분할 수 없어 **탐지 신호가 사라진다.**
  `used` 마킹 + `family_id`로 남겨야 한다.

- **"회전은 모든 엔드포인트에서 일어나야 한다"**
  → 그게 바로 고아 토큰·토큰 증발·랜덤 로그아웃의 **원인**이었다. 회전은 전용 엔드포인트 한 곳에서만.

- **"동시 요청 5개면 DB에 R1이 남는다"**
  → R1은 사라지고 **유효한 고아 토큰 5개**가 남는다. 인증 수단이 늘어 공격 표면이 넓어진다.

- **"쿠키는 다른 사이트에서 온 요청에는 안 실린다"**
  → **기본적으로 실린다.** 그래서 CSRF가 성립하고, 그걸 막는 속성이 `SameSite`다.

- **"유예 구간 안의 요청에는 다시 재발급해 준다"**
  → 재발급하면 회전이 또 일어나 유예 구간을 둔 의미가 없다.
  **회전 없이 직전 발급분을 그대로 재응답(멱등)** 해야 한다.

- **"재사용 탐지 시 그 토큰 하나를 거절하면 된다"**
  → 공격자는 이미 다음 토큰으로 갈아탔다. **체인 전체 폐기**여야 의미가 있다.

- **"`/auth/refresh`로 모으면 고아 토큰이 1개 생긴다"**
  → **0개**다. 새 토큰은 `Set-Cookie`로 브라우저가 자동 저장하므로 주인이 확실하고,
  이전 토큰은 `used`로 마킹되어 더 이상 유효하지 않다. "유효한데 주인 없는 토큰"이 생길 자리가 없다.

## Q&A

**Q. 애초에 왜 리프레시 토큰을 회전시키나?**
A. 회전이 없으면 토큰을 탈취한 공격자가 만료일까지 무제한으로 액세스 토큰을 재발급받을 수 있다.
회전을 걸면 "이미 소비된 토큰이 다시 들어오는" 사건이 탈취의 증거가 되어 서버가 탈취를 **탐지**할 수 있다.

**Q. 한 페이지가 js·css·이미지를 동시에 요청하면 필터의 회전 로직은 어떻게 되나?**
A. 스레드 N개가 동일한 R1을 "유효" 상태로 동시에 읽고 각자 회전한다.
R1은 사라지고 유효한 토큰 N개가 생기며, 클라이언트는 그중 하나만 받는다(정적 리소스 응답은 JS가 못 읽어 아예 못 받는다).
나머지는 고아 토큰이 되고, 재사용 탐지는 발동하지 않는다.

**Q. 그럼 `used` 플래그 + family 방식으로 제대로 구현하면 해결되나?**
A. 문제가 사라지는 게 아니라 **옮겨간다**. 이번엔 스레드 2~N이 "이미 쓰인 토큰의 재유입"으로 판정되어
체인 전체가 폐기되고 **정상 사용자가 랜덤 로그아웃**된다. 그래서 grace period가 필요하다.

**Q. 필터에서 JSON을 응답하면 CSS 요청은 어떻게 되나?**
A. `write()` 후 `doFilter()`를 부르면 응답이 이미 커밋되어 `IllegalStateException` 또는 JSON+CSS가 섞인 바디가 나간다.
`doFilter()`를 안 부르면 CSS가 안 나간다. 어느 쪽이든 정상 동작이 불가능하다.

**Q. 401이 4개 돌아오면 axios 인터셉터는 `/auth/refresh`를 몇 번 부르나?**
A. 아무 처리도 안 하면 4번. single-flight로 갱신 Promise를 공유해 1번으로 줄이고,
나머지는 그 Promise를 `await`한 뒤 원래 요청을 재시도한다.

**Q. `used` 토큰이 200ms 뒤에 온 것과 3일 뒤에 온 것을 똑같이 취급해도 되나?**
A. 안 된다. 200ms는 정상 동시 요청일 가능성이 압도적이므로 멱등하게 직전 발급분을 재응답한다.
3일 뒤는 정상 클라이언트라면 이미 새 토큰으로 갈아탔을 시간이므로 탈취로 보고 체인 전체를 폐기한다.

## 다음 학습

- grace period 안에서 "직전 발급분을 그대로 재응답"하려면 이전 토큰 행에 무엇을 어떻게 보관해야 하나 (스키마 설계)
- `family_id` 기반 체인 폐기의 실제 테이블 설계와 인덱스 (기존 노트 `deterministic-hash-for-lookup` 와 연결)
- 조건부 갱신(`UPDATE ... WHERE used = false`)과 DB 트랜잭션 격리 수준의 관계 — 격리 수준만으로 이 경합을 막을 수 있나
- Spring Security 필터 체인에서 정적 리소스를 어떻게 제외하는가 (`WebSecurityCustomizer` / `securityMatcher`)
- `SameSite=Strict` 와 `Lax` 의 실제 차이, 그리고 SPA + 별도 API 도메인 구성에서의 쿠키 전략
- 리프레시 토큰 만료 자체와 슬라이딩 세션(sliding expiration)의 트레이드오프
