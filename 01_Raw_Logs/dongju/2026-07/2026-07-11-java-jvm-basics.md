# Java의 동작 원리와 기초

study-interview 세션. "Hello.java가 실행되기까지"를 소재로 컴파일 파이프라인 → JVM 구성요소 → 메모리 구조 → GC 순으로 검증했다.

## 배운 개념

### 실행 파이프라인과 WORA (What & Why)

- `.java`(소스코드) → `javac`(컴파일러) → **`.class` 파일(바이트코드)** → JVM에서 실행.
- 바이트코드는 기계어도 소스코드도 아닌 **JVM 전용 중간 코드**. OS가 아니라 JVM이 읽는다.
- **WORA(Write Once, Run Anywhere)**가 가능한 구조: 바이트코드는 어느 플랫폼에서나 동일하고, OS별 차이는 **OS마다 따로 구현된 JVM**(Windows용/Mac용/Linux용)이 흡수한다. C/C++처럼 타깃 기계어로 바로 컴파일하면 OS·아키텍처마다 다시 빌드해야 하는 Pain Point를 해결한 설계.

### JVM 3대 구성요소 (How & Structure)

1. **클래스 로더** — `.class` 파일을 읽어 메모리에 적재.
2. **런타임 데이터 영역** — 적재된 코드·데이터가 놓이는 메모리 공간(스택, 힙 등).
3. **실행 엔진** — 바이트코드를 기계어로 변환해 실행.

### 실행 엔진의 하이브리드 전략 — 인터프리터 + JIT

- **인터프리터**: 바이트코드를 한 줄씩 읽어 즉시 실행. 시작이 빠르지만, 같은 코드가 반복되면 매번 처음부터 다시 읽어 느리다.
- **JIT 컴파일러**: 코드 구간을 통째로 기계어로 컴파일해 캐싱. 컴파일 비용이 크지만 한번 해두면 이후 실행이 빠르다.
- **둘 다 필요한 이유(트레이드오프)**:
  - 인터프리터만 쓰면 → 반복 실행되는 코드가 계속 느리다.
  - 전부 JIT으로 컴파일하면 → 프로그램 **시작이 느려지고**, 딱 1번 실행되고 버려질 코드에 들인 컴파일 비용이 낭비된다.
- 그래서 JVM은 메서드/루프마다 **호출 횟수 카운터**를 두고, **임계값(threshold)을 넘은 자주 실행되는 구간 = 핫스팟(HotSpot)**만 골라 JIT 컴파일한다. Oracle 기본 JVM 이름이 "HotSpot JVM"인 이유.

### 메모리 구조 — 스택 vs 힙

```java
public void order() {
    int count = 3;
    Pizza p = new Pizza("페퍼로니");
}
```

- `count`(기본형 지역변수) → **스택**.
- `new Pizza(...)`로 만든 객체 → **힙**.
- `p` → 스택에 있고, 안에는 객체 자체가 아니라 **힙 객체의 주소(참조)**가 담긴다.
- 메서드가 끝나면 스택의 `count`/`p`는 프레임과 함께 자동 제거. 힙의 객체는 GC 몫.
- **스레드 관점의 결정적 차이**:
  - **스택 = 스레드마다 1개씩(thread-private)**. 스레드가 3개면 스택도 3개. 다른 스레드가 내 지역변수를 참조할 방법이 없으므로 지역변수는 **태생적으로 스레드 안전**.
  - **힙 = 전체 스레드가 공유하는 단 1개**. 그래야 스레드끼리 객체를 주고받을 수 있다. 대신 여러 스레드가 같은 객체를 동시에 건드릴 수 있어 — **자바 동시성 문제의 구조적 뿌리**가 여기다.

### GC와 한계 상황 (Edge Cases & Trade-offs)

- GC 판정 기준: **GC Root(스택의 변수 등 출발점)에서 참조를 따라가 도달할 수 없는(unreachable) 객체 = 수거 대상**. "재사용 안 될 것 같은 객체"를 예측하는 게 아니라, 기계적인 도달 가능성 검사다.
- **StackOverflowError**: 무한 재귀 → 메서드 호출마다 스택 프레임이 쌓임 → 스택 고갈.
- **OutOfMemoryError**: 리스트에 객체를 무한히 담으면 힙이 차는데, **리스트가 참조를 유지하고 있어 GC Root에서 도달 가능** → GC가 살아있는 객체로 판단해 못 치운다. GC가 있어도 OOM이 나는 이유.
- **Stop-the-World**: GC가 힙을 청소하는 동안 애플리케이션 스레드가 멈춘다(청소 중에 객체가 계속 움직이면 정확한 수거가 불가능하므로). 게임 서버·초저지연 시스템에서 Java가 불리하다고 지적받는 GC의 대가.

## 오답·헷갈린 점

- **"javac 파일로 컴파일된다"** → `javac`는 컴파일러(명령어) 자체이고, 산출물은 **`.class` 파일(바이트코드)**. 도구 이름과 결과물을 혼동했었다.
- **"GC는 재사용되지 않는 / young 힙의 객체를 지운다"** → 판정 기준은 **도달 가능성(reachability)**. young/old 세대는 "어디를 언제 청소하나"(장소·타이밍)의 문제이지 쓰레기 판정 기준이 아니다. 두 개념이 섞여 있었다.
- **"힙이 스레드마다 3개"** → 정반대. **스택이 스레드마다 1개씩, 힙은 공유 1개**. 힙이 스레드별로 분리되면 스레드 A가 만든 객체를 B가 영영 볼 수 없어 객체 공유 자체가 불가능해진다.

## Q&A

- **Q. 인터프리터와 JIT은 왜 공존하나? 하나만 쓰면 안 되나?**
  A. 인터프리터만 쓰면 반복 코드가 느리고, 전부 JIT하면 시작이 느려지고 1회성 코드에 컴파일 비용이 낭비된다. 그래서 인터프리터로 빠르게 시작하고, 호출 카운터가 임계값을 넘은 핫스팟만 JIT 컴파일하는 하이브리드.
- **Q. JVM은 "자주 쓰이는 코드"를 어떻게 아나?**
  A. 메서드·루프별 실행 횟수 카운터가 임계값을 넘으면 핫스팟으로 판정.
- **Q. GC가 있는데 왜 OutOfMemoryError가 나나?**
  A. 참조가 유지되는 객체는 GC Root에서 도달 가능하므로 GC가 수거하지 않는다. 살아있는(참조되는) 객체만으로 힙이 차면 OOM.
- **Q. 지역변수는 왜 스레드 안전한가?**
  A. 스택은 스레드마다 독립적으로 존재해서 다른 스레드가 접근할 경로 자체가 없다.
